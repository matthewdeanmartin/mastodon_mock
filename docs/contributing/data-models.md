# Data models

The database is a small, stateful representation of the Mastodon resources that clients
exercise. SQLAlchemy models in `mastodon_mock/db/models.py` are the runtime mapping; the
Alembic revisions in `mastodon_mock/alembic/versions/` are the schema history. When they
disagree, fix the migration rather than relying on `Base.metadata.create_all()` to hide the
drift.

## How to read the model

Most records use a `BigInteger` primary key generated by `ids.next_id()`. API serializers
convert those integer IDs to strings because Mastodon exposes its `IdType` as a string.
Foreign keys express relationships between resources; join tables express many-to-many
edges. JSON columns are used for Mastodon-shaped arrays or objects whose internal shape is
not queried by the mock (for example account profile fields and poll options' metadata).

The main graph looks like this:

```text
Account ──< Status ──< StatusMention >── Account
   │          │
   │          ├──< MediaAttachment
   │          ├── Poll ──< PollOption ──< PollVote >── Account
   │          └── StatusTag
   │
   ├──< OAuthToken >── OAuthApp
   ├── Relationship >── Account       (directed source → target edge)
   ├── Favourite / Bookmark / Pin / StatusMute >── Status
   ├── UserList ──< UserListAccount >── Account
   └── Notification (actor, recipient, and optional status)
```

The graph is intentionally pragmatic rather than a complete Mastodon production schema.
For example, `Status.content` and `Status.text` retain the rendered and plain-text forms
needed by different API responses, while `Account.fields`, OAuth scopes, and poll options
are JSON lists because the mock does not need relational queries over their members.

## Model families

| Family | Models | Purpose |
| --- | --- | --- |
| Identity and auth | `Account`, `OAuthApp`, `OAuthToken`, `AccountSettings`, `Invite` | Users, app registration, bearer-token lookup, and account configuration |
| Posts and media | `Status`, `MediaAttachment`, `Poll`, `PollOption`, `PollVote` | Status content, attachments, polls, replies, reblogs, and quotes |
| Edges and interactions | `Relationship`, `Favourite`, `Bookmark`, `Pin`, `StatusMute`, `StatusMention`, `StatusTag`, `FollowedTag`, `FeaturedTag` | Account-to-account and account-to-status state |
| Timelines and notifications | `Notification`, `ConversationRead`, `Marker`, `ScheduledStatus` | Derived activity exposed by timeline and notification endpoints |
| Lists, filters, and announcements | `UserList`, `UserListAccount`, `Filter`, `FilterKeyword`, `FilterStatus`, `Announcement`, `AnnouncementDismissal`, `AnnouncementReaction` | User-curated views and instance notices |
| Moderation and administration | `Report`, `DomainBlock`, `AdminDomainBlock`, `AdminDomainAllow`, `AdminEmailDomainBlock`, `AdminCanonicalEmailBlock`, `AdminIpBlock`, `TrendReview`, `NotificationPolicy`, `NotificationRequest`, `NotificationPolicyOverride` | Admin and moderation surfaces |
| Integrations and support state | `PushSubscription`, `Idempotency`, `SuggestionDismissal` | Push delivery, idempotency keys, and dismissed suggestions |

## Adding or changing a model

1. Decide whether the state is durable. If a later request must observe it, add a model or
   column; do not keep it only in a router-local dictionary.
2. Add typed SQLAlchemy fields and a clear docstring in `db/models.py`. Use `BigInteger` IDs,
   `ForeignKey` constraints, indexes for lookup/pagination columns, and a uniqueness
   constraint where duplicate edges would be invalid.
3. Create and review an Alembic revision:

   ```bash
   uv run alembic revision --autogenerate -m "describe the schema change"
   uv run alembic upgrade head
   ```

4. Update seed/sample data only if the new state is required for a normal fixture or demo.
5. Update the serializer and route, then add a router/integration test. If a real Mastodon.py
   method can observe the change, add a contract test as well.
6. Run `make test` and the migration drift test. Check both a fresh database and an upgraded
   database; old rows must remain readable.

## Semantics to preserve

- IDs are monotonic integers internally and string IDs externally.
- Timestamps are timezone-aware UTC values from `utcnow()`.
- Account relationships are directed: a row's `source_account_id` is the caller and
  `target_account_id` is the other account.
- Status replies, reblogs, and quotes are self-referential foreign keys; nullable means the
  status is a standalone post.
- Delete-orphan cascades are appropriate for owned children such as `PollOption`; do not
  cascade across independent resources such as accounts and statuses without checking API
  behavior first.
- A model field is not automatically part of the public API. Add or adjust the corresponding
  serializer deliberately, with tests for both authenticated and anonymous views where they
  differ.

For the request-layer consequences of these choices, continue to [Architecture](../overview/how-it-works.md#for-contributors).
